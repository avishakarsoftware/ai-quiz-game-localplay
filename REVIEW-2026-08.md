# Repo Review — Weak Areas (2026-08-04)

A full-repo review across product, technical architecture, and test coverage. Every technical claim
below was verified by reading the code at the cited `file:line` this day; product claims are grounded
in what the code/config actually does, not in speculation. Findings marked **(tracked)** are already
documented in a spec or backlog — they appear here anyway because this is a complete map, not a
novelty report. Effort sizing: **S** < half a day, **M** = 1–3 days, **L** = a week+.

Overall shape: this codebase is in much better health than its size suggests — CI is real (backend +
live-Postgres parity + typecheck + build), the money rails are atomic and idempotent, WS auth is
constant-time, and the catalog/coverage guard pattern is genuinely good engineering. The weaknesses
cluster in four places: **the deploy/ops story trusts luck**, **two god files carry the whole
product**, **the growth features are built but invisible**, and **the paywall fires at the worst
moment in the product**.

## O. Ops, deployment & reliability

### O0. Prod is 9 days behind master with known fixes undeployed — **act first**
`DEPLOY.md:74`: prod = `b0c1fc03` (2026-07-26), gamma = `2820ee2f` (2026-08-04). The undeployed
delta includes the `/purchases/restore` re-mint gate and the prompt-fence hardening — i.e. the two
security-relevant fixes from the July session are live-broken in prod right now. Not a code
weakness; a state weakness. **Fix (S): deploy prod after the current gamma bake.**

### O1. Deploy is stop-old-then-start-new with no rollback
`scripts/deploy-gcp.sh:420-455`: the old container is `docker stop`/`docker rm`'d **before** the new
one starts; the health check (20×1s on `/health`) then merely `exit 1`s on failure. A bad image
doesn't roll back — it leaves **nothing running**. The script's own error message tells you to go
read logs while prod is down. Deploys also require the laptop (no CI-built images), so a deploy
during travel = untested path.
**Fix (S–M):** start the new container under a temp name on a spare port → health check → swap
(`docker rename` or nginx upstream flip) → remove old. Keep the previous image tagged
(`revelry-backend:prev`) and auto-restart it when the health check fails. ~30 lines of script.

### O2. No monitoring or alerting of any kind
No uptime check, no error tracker, no disk watch, no webhook-failure alarm — `grep -ri
"sentry|uptime|alert"` across scripts/, .github/, Makefile finds nothing. Today, discovery of an
outage is "Avi notices." A Stripe webhook that 500s for three days (Stripe gives up after ~3 days of
retries) would silently eat purchases.
**Fix (S):** (1) GCP Uptime Check on `https://gamesapi.revelryapp.me/health` + alert policy to
email — free tier, ~30 min. (2) Sentry (or GlitchTip self-hosted on the same VM) for backend
exceptions — the FastAPI integration is ~5 lines. (3) A daily cron on the VM that alerts on disk
>80% and `docker ps` health. These three cover ~90% of realistic failure modes.

### O3. Prod and gamma share one VM
Both containers, plus nginx, on `revelry-backend` (`us-central1-a`). A gamma deploy that pegs CPU
during an on-VM image build (`--build-on-vm`), or a runaway gamma container, degrades prod. Accepted
for cost — but unbounded.
**Fix (S):** add `--memory=512m --cpus=1` to the gamma `docker run` in the deploy script so gamma
can never starve prod. Moving gamma to a separate e2-micro later is optional; the resource caps are
the cheap 90%.

### O4. Backup/restore has never been rehearsed
Supabase platform backups are assumed but no restore has ever been tested, and there's no
documentation of which tier/PITR window applies. The IONOS-hosted media (user uploads) has no backup
story at all. SQLite-era data on the VM (`revelry-data/`) has a backups dir provisioned
(`deploy-gcp.sh:171`) but nothing writes to it.
**Fix (M):** document the Supabase backup tier; rehearse one restore into a scratch project; add a
weekly `rsync` of IONOS media to the VM or GCS. A backup that has never been restored is a hope, not
a backup.

### O5. Python version skew: prod container 3.12, dev/CI 3.14
`backend/Dockerfile:1` = `python:3.12-slim`; `.github/workflows/ci.yml` and the local venv = 3.14
(the CI comment even says "match the local dev venv"). All 1,419 backend tests run on an interpreter
prod never uses. Real risk is low but nonzero (asyncio/timing behavior differs across versions — and
this codebase is timing-sensitive, see T5).
**Fix (S):** bump the Dockerfile to `python:3.14-slim`, redeploy gamma, watch, promote.

### O6. Secrets adjacent to the repo
`SubscriptionKey_5X98927GH9.p8` (Apple), `revelryapp-d48cc633d44b.json` (GCP service-account key),
`db_token_localplay` sit at the repo root. They **are** gitignored and untracked (verified) — but
they live in a Desktop folder one `git add -f`, one cloud-sync, or one screen-share away from
exposure, and GCP SA JSON keys are non-expiring.
**Fix (S):** move them into `backupenv/` (the established secret store), and rotate the GCP SA key
to a short-lived workload-identity or at least a fresh key after relocation.

## P. Product

### P1. The paywall fires mid-party, at the worst moment in the product
The economy math (`backend/config.py:151,199,200`): signup grant **20** sparks, a room costs **10**,
a generation costs **1**. A brand-new host gets roughly **two games** before hitting 402 — which
means the paywall interrupts a *live party*, with friends watching, mid-flow. `paywall_hit` events
are tracked per source (`OrganizerPage.tsx:1104,1282,1331`), so this is measurable — but the funnel
design guarantees the ask lands under maximum social pressure with minimum privacy.
**Fix (M), pick one deliberately:**
- **First-party grace:** first N hours after first room are free (session-scoped flag), so the ask
  arrives *after* a great first party, via "that was fun — keep hosting" framing.
- **Party pricing instead of game pricing:** one charge unlocks the evening (matches how Jackbox
  frames value); sparks then meter generation only.
- Cheapest variant: raise the signup grant to ~35 (3 games) and move the ask to the podium screen of
  game 3 — a calm moment — instead of a 402 error modal.
The current "error modal with upgrade button" (`OrganizerPage.tsx:306`) monetizes failure; every
alternative above monetizes success.

### P2. Every growth feature is buried in the Settings drawer
Referral, gifting, achievements, and stats are all built, tested, and live-flagged — and all render
**only** inside `SettingsDrawer.tsx` (verified by grep: no other page imports `ReferralSection`,
`GiftSection`, `AchievementsSection`, `StatsSection`). The podium — the emotional peak, whole group
watching — shows Share + Play Again (`OrganizerPage.tsx:3129-3130`) and nothing else. Nobody opens a
settings drawer at a party.
**Fix (S–M):** podium-moment hooks: badge-earned toast on the podium itself; a "Both get 20 ⚡"
referral CTA on the *player* podium (each guest is a prospective host with the app already open —
this is the entire viral loop, currently invisible); streak/stats teaser on return visits.

### P3. The catalog leads with the alphabet, not the shelf
`PartyHubPage.tsx:391-429`: default view is **all ~37 games, alphabetically** — the store window
leads with "Acronym Game." "Most Popular" exists but as an opt-in pill; occasion games (Wedding/
Baby/Holiday bingos) are scattered by letter rather than shelved together. 37 undifferentiated cards
is choice paralysis for a cold host with guests waiting.
**Fix (S–M):** default to a curated layout — "Start here" row (3–4 proven crowd-pleasers), "Most
Popular" row (the ranking already exists in `gameModes.ts`), occasion shelf, then A–Z below. Pure
frontend; catalog data already carries the metadata.

### P4. The between-games moment is unexploited
Play Again + room reuse works (`OrganizerPage.tsx:1717` — connected players carry over, well built).
But when a game ends there is no "try this next" — no similar-game suggestion, no "your group liked
X, groups like yours play Y." In a party product the between-games moment *is* the retention
mechanic; every ended game currently dead-ends into the same-game loop or a walk back through the
37-card catalog.
**Fix (M):** a 2–3 card "next game" strip on the organizer podium, seeded with static curated
pairings (quiz→bluff, impostor→mafia…) — no ML needed. The catalog metadata (player counts, pace)
supports it today.

### P5. Nothing brings anyone back tomorrow
The entire retention loop is the daily streak bonus — which pays out silently inside the balance
call. There is no push infrastructure at all (verified: no FCM/APNs/`PushNotifications` anywhere in
backend or the Capacitor config), no email capture beyond OAuth sign-in, no re-engagement surface.
Native apps are shipped on both stores; they're inert once closed.
**Fix (L, staged):** Capacitor push plugin + FCM/APNs (M just for plumbing), then two notifications
only: streak-about-to-break and "your group played X days ago." Until then (S): the share card is
the only artifact that leaves the party — put the download/app-store QR on the *shared result page*
(`share.py` renders it; check what a recipient actually sees) so each shared podium recruits the
next host.

### P6. Monetization is single-instrument
Only consumable spark packs (3 SKUs, `config.py:234`). No host pass/subscription for the repeat
host, no ads for the never-pay cohort — **(tracked)** `SPEC-ADS.md` is written and blocked on an
AdMob account; the client-trusted ad endpoint is correctly 403-locked meanwhile. Party hosts are the
textbook subscription persona (recurring social events, price-insensitive relative to the evening).
**Fix (M):** a monthly "Host Pass" SKU (unlimited rooms, metered generation) via the existing
RevenueCat + Stripe rails — both support subscriptions with modest wiring. Revisit after P1 settles
the pricing model.

## A. Backend architecture

### A1. `socket_manager.py` is a 6,753-line god module — and it's where every game lands
Two classes: `Room` (:322) and `SocketManager` (:947 → EOF, ~5,800 lines). The engines themselves
are clean (`engine_common.py` protocol, pure-logic modules), but the *integration* layer — the
`_start_<game>` / `_sync_<game>_phase_to_room` / `_sync_<game>_scores_to_players` /
`_<game>_public_state` method families — exists **per game, on one class**, for ~25 games. Adding a
game means threading it through the god class in 3–6 places; a mistake in one game's handler can
break the message loop for all of them. The `Room` class likewise carries per-game fields
(`mafia_timer_task`, housie undo state, drawing order…) for every game at once — which is exactly
how today's teardown bug happened (three cancellable task fields, teardown knew about two).
**Fix (L, but incremental and mechanical):** a `GameSocketAdapter` registry mirroring the pattern
`game_catalog.py` already proved: each game gets a module owning start/sync/public-state/message
handlers; `SocketManager` keeps only transport, auth, and dispatch. Migrate one game per sitting —
the `_start_*` families are nearly copy-paste-separable today. Stop the bleeding now (S): require
new games to ship as adapters even before old ones migrate.

### A2. `main.py`: 106 endpoints in one 6,468-line module
Rooms, content authoring, tokens, checkout, webhooks, admin, share, media, stats, referrals — one
file. It works, but every merge conflict, every review, and every navigation pays the tax.
**Fix (M):** FastAPI `APIRouter` split along the seams that already exist in the file's own section
comments (tokens/economy, checkout+webhooks, admin, share, media, content, rooms). Pure mechanical
move, no behavior change; do it before the next feature lands another 500 lines.

### A3. Fire-and-forget asyncio tasks with no exception surface
`socket_manager.py:5274`: `asyncio.create_task(self._mc_complete_game(room))` — no reference kept
(GC can collect a running task) and no done-callback (an exception is reported only at event-loop GC
time, if ever). The other `create_task` sites (:957, :970, :1014, :1346, :4791) at least keep
references but none installs an error callback either — a crashed snapshot loop or question timer
dies silently and the feature just… stops.
**Fix (S):** one `spawn(coro, name)` helper that keeps a strong reference and logs exceptions via
`add_done_callback`; mechanical replacement at 14 sites. Pairs naturally with O2 (Sentry would then
actually see these).

### A4. Accepted-design notes (not findings)
Single uvicorn process with in-memory rooms is a deliberate design with a documented sharding plan
(`hash(room_code) % N`), and deploy survival is mitigated by room snapshots (verified: default-on,
10s interval, `config.py:100-101`). Fine at current scale. The first real ceiling is one CPU
saturating on WS fan-out in large rooms — measure before re-architecting.

## D. Data layer

### D1. The `_SUPABASE_EXPORTS` three-place sync has no guard
Adding a db function that must differ on Supabase requires: the `db.py` impl, the `supabase_db.py`
impl, **and** the name in `_SUPABASE_EXPORTS` (`db.py:2270+`). Forget the third and prod silently
runs the SQLite implementation against the container's **ephemeral** disk — no error, plausible
return values, data written to a file that vanishes on next deploy. `test_runtime_db_guard.py`
guards backend *selection* only, not override completeness; nothing guards this today, and the
memory notes show the referral wrappers nearly missed the list once already.
**Fix (S):** a test asserting (a) every public function in `supabase_db.py` appears in
`_SUPABASE_EXPORTS`, and (b) every `db.py` function whose body touches the wallet/user/entitlement
tables is either in the list or in an explicit `_SQLITE_ONLY` allowlist with a comment. Direction
(a) alone is 10 lines and catches the deadly case.

### D2. Non-atomic multi-write on the REST backend
The money paths are properly atomic — every credit/debit/gift/referral/purchase goes through a
Postgres RPC (`supabase_db.py:349-660`, verified). But `merge_device_to_user` does **two separate
REST updates** (entitlements `:282`, then device_usage `:283`) with no transaction: a failure
between them leaves a half-merged identity. Low frequency, annoying to repair.
**Fix (S):** fold both updates into a `merge_device_rows` RPC like the others; the SQL template
pipeline already exists.

### D3. Schema changes have no versioning spine
Migrations are "author SQL via template → apply via Management API, gamma first" — disciplined in
practice (DEPLOY.md documents the two-step), but there is no `applied_migrations` table, so nothing
records what ran where; correctness depends on the operator and the ledger doc. The
gifting-idempotency episode (a later migration silently replacing an earlier function body — order
load-bearing) is exactly the failure class a version spine prevents.
**Fix (M):** numbered migration files + a tiny `schema_migrations(prefix, name, applied_at)` table +
a 30-line apply script that refuses out-of-order application. Keep the Management-API transport;
just add the bookkeeping.

## S. Security

Posture is genuinely good — worth saying explicitly: organizer WS auth is a first-frame `AUTH`
message checked with `hmac.compare_digest` (`socket_manager.py:1137-1142`, *not* a query param —
the old externalization concern was fixed), admin auth is constant-time bearer compare
(`main.py:6240-6247`), share-card HTML escapes all user strings (`share.py:116-118`), Stripe/RC
webhooks verify signatures, prices are server-authoritative (`main.py:5571,5602`), proxy headers are
gated behind `TRUST_PROXY_HEADERS`. Remaining items:

### S1. Rate-limit bypass via X-Forwarded-For's client end
`main.py:256-259`: with `TRUST_PROXY_HEADERS` on, the code takes `forwarded.split(",")[0]` — the
**leftmost** entry, which is client-supplied when nginx appends via `proxy_add_x_forwarded_for`. Any
client can send `X-Forwarded-For: <random>` per request and rotate identities past every IP rate
limit (including the LLM and checkout limiters).
**Fix (S):** take the **last** element (the one your own proxy appended), or prefer `X-Real-IP` and
set it authoritatively in the nginx config. Verify against the actual nginx server block on the VM.

### S2. Device-UUID minting farms signup grants
`tokens.py:56,64`: any fresh UUID presented as `X-Device-Id` gets a wallet with the 20-spark signup
bonus — no per-IP creation throttle. The global `MAX_LLM_CALLS_PER_HOUR` budget (`main.py:287`)
caps the *dollar* exposure well, but that means the attack degrades into a **DoS on the shared
generation budget**: a farmer's minted wallets consume the hourly LLM allowance that real users
needed. (This is also the honest reason the ad-reward endpoint stays locked — same wallet-minting
economics.)
**Fix (S–M):** per-IP wallet-creation throttle (e.g. 5/day — legitimate parties share one IP but
players don't all create *organizer* wallets), plus a per-wallet daily generation quota so no single
identity can drain the global pool.

### S3. Local secret hygiene — see O6.

## M. Payments & economy

Verified strengths first: `credit_purchase` is transactional and reference-idempotent
(`db.py:1370-1430`), webhook events are marked processed **after** business logic with refund
failures re-raised so Stripe retries (`main.py`, refund path), restore is entitlement-gated against
re-minting, deleted accounts can't be resurrected by late webhooks (`db.py:1393-1406` — genuinely
careful code). Remaining:

### M1. Paid-but-credited-zero at the balance cap **(tracked — product decision pending)**
`db.py:1416`: `new_balance = max(current, min(current + amount, MAX_TOKEN_BALANCE))` — at or near
`MAX_TOKEN_BALANCE` (1,000), a real-money purchase credits partially or **zero**. Auditable
(`actual_credit` lands in the ledger) but indefensible to the customer, and on iOS it's the kind of
thing that loses an appeal.
**Fix (S):** block the purchase *before* payment — grey the pack in `SparkPurchaseModal` and reject
in `/checkout/create` when `balance + pack > cap`, message "you're nearly full." Alternative: cap
only free-earned sparks and let purchased sparks exceed it. Either beats taking money for nothing.

### M2. No "where's my purchase" runbook
The data to reconstruct any complaint exists (ledger + entitlement audit rows + `/admin/lookup`),
but no documented procedure ties provider event → wallet → resolution. At current volume fine;
first angry customer, you'll want it written.
**Fix (S):** one page in DEPLOY.md: given a Stripe session / RC transaction id, the three queries to
run and the `/admin/grant` remediation with its guardrails.

## T. Testing

Context: 1,419 backend + 388 frontend tests pass; CI runs backend, live-Postgres parity, `tsc -b`,
vitest, and the production build on every push. The gaps are about *what kind* of coverage, not
volume:

### T1. The full-stack game suite runs in no CI
`ci.yml` contains zero Playwright: not `all-games.spec.ts` (the canonical every-game-playable
suite, complete with its own drivability guard `test_e2e_game_coverage.py`), not the 16-shot visual
suite. They run when someone remembers on a laptop. The catalog can regress a game and CI stays
green — the exact class of miss that let the bingo/drawing baselines rot for two months (fixed
today, SPEC-TESTING §8b-2).
**Fix (M):** a third CI job: boot the backend (SQLite mode), `playwright install chromium`, run
`all-games.spec.ts` + the visual suite against the local stack. The live-gamma specs stay manual.
~20 min of CI time; make it required.

### T2. Engine coverage is deep on logic, thin on transport
24 of 27 engines have unit tests, but only **5** (`generic_prompt`, `impostor`, `mafia`,
`odd_question`, `party_quests`) have backend socket-level tests. The other 19 rely on the all-games
Playwright pass for their transport layer — which (T1) isn't in CI, and which drives the happy path
only. Reconnection-mid-game, organizer drop/reclaim, and snapshot-restore-under-load are exercised
for the general machinery (`test_websocket_async.py`) but not per-game.
**Fix (M, amortized):** when a game's socket bugs surface, pay the cost then — but require socket
tests for **new** games now (the `impostor` suite from this week is the template).

### T3. The most valuable page has the least coverage
`OrganizerPage.tsx` — 3,174 lines, a 40+-state union (`:64`), every paywall trigger, every game's
host flow — is imported by **zero** tests (verified). 30 of 76 components have no direct test,
including `PodiumScreen` (the share/monetization moment) and most per-game boards. Meanwhile
utilities are lavishly tested. Coverage is inversely proportional to blast radius.
**Fix (M):** don't chase 3,174 lines with unit tests — extract the WS-message dispatch into a
testable reducer first (F1), test *that*, and add component tests only for `PodiumScreen` +
`SparkPurchaseModal` (the money surfaces).

### T4. Nobody measures coverage
`pytest-cov` is installed and never invoked; no coverage job, no floor, no report artifact. All
statements about coverage in this repo (including this review's) are inferred from file mapping
rather than measured.
**Fix (S):** add `--cov=. --cov-report=xml` to the CI backend job + a Codecov/artifact upload. Don't
gate on a number yet — just make the truth visible; T3-style inversions become obvious in one
report.

### T5. Known residual flake **(tracked — SPEC-TESTING §8d)**
`test_e2e.py` still fails ~1/25 full-file runs (same test, 15s stall, clean in isolation), after
today's 4× reduction. Instrumented to self-describe on next occurrence. Left open deliberately;
don't bisect it one run per step.

version skew is filed as O5. Frontend a11y and mobile-viewport testing don't exist anywhere —
acceptable for now, noted for the record.

## F. Frontend architecture

### F1. Three god pages re-implement the same message loop
`OrganizerPage.tsx` (3,174), `PlayerPage.tsx` (2,254), `SpectatorPage.tsx` (1,419) each hold a giant
WS `msg.type` switch plus per-game branches; the organizer's state union alone lists 40+ states in
one type (`OrganizerPage.tsx:64`) and duplicated state lists appear inline (`:335`). Per-game
*screens* are partially extracted (good — `components/organizer/*`, `MafiaGame`, `passplay/*`), but
the shells accrete every new game's wiring. This is A1's mirror image, and it's why OrganizerPage is
untestable (T3).
**Fix (L, incremental):** a typed message-dispatch registry per role (map `msg.type` → handler),
per-game client state machines colocated with their components, pages reduced to transport + layout.
Same migration discipline as A1: new games must ship this way immediately; old games move
opportunistically.

### F2. A 1.26 MB main chunk with zero code splitting
Build output: `index-*.js` = 1,264 kB minified (371 kB gz) — every game board, the TV app, the
authoring editor, and the admin surfaces download before a player can tap a single answer button.
Party guests join on phones, on party Wi-Fi.
**Fix (S–M):** `React.lazy` at the route level first (TV home, authoring, spectator), then per-game
board components on selection. The seams already exist; a weekend's work halves first-paint for
players.

### F3. `types.ts` is a 1,020-line dumping ground
Shared WS message types, per-game payloads, and page-local shapes in one file — every game touches
it, so it's a merge-conflict magnet and hides which types are actually shared.
**Fix (S, fold into F1):** split per-game types next to their components; keep only transport +
cross-game contracts central.

### F4. 7,100 lines of hand-written global CSS
One namespace, no scoping; the Tailwind-shim episode (SPEC-TESTING §8a) proved how silently it can
drift from the markup. Mitigated now by the 16-shot visual suite + the shim guards, so this is
watch-not-fix. If it grows another few thousand lines, consider CSS modules for new components only.

## What I did *not* find (checked and clean)

- SQL injection: all SQLite access is parameterized; the one dynamic `assignments` builder
  (`db.py:2262`) interpolates **column names from a server-side dict**, not values.
- Secrets in git history: the sensitive files at root are untracked and gitignored (verified via
  `git ls-files`); nothing key-like is tracked.
- Stripe/RevenueCat: signature verification present, prices server-side, replay-idempotent at two
  layers, refunds re-raise for retry. The money rails are the best-engineered part of the repo.
- WS abuse: origin checks, 10 msg/s rate cap, 4 KB size cap, room/quiz TTL eviction all present.
- The catalog/coverage guard pattern (`test_e2e_game_coverage.py` + waivers) — this is the pattern
  the rest of the repo should copy, and several fixes above are just "apply it to X."
